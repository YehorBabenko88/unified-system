## 1. Цель

Встроить в существующий Unified устойчивый механизм автоматизации, который позволит:

- Разрабатывать и интегрировать компоненты параллельно.
- Автоматически проверять готовность новых версий.
- Обнаруживать проблемы на каждом Windows-узле.
- Восстанавливать работу после сбоев.
- Безопасно устанавливать и обновлять компоненты.
- Сохранять историю всех действий.
- Продолжать незавершённые задания после restart.
- Снижать необходимость ручного управления через Codex.
- Управлять всей инфраструктурой из Terminan.

Не создавать новый независимый оркестратор вместо Unified.

Не устанавливать Codex Desktop на каждый компьютер как обязательную часть системы.

Codex остаётся инструментом разработки и анализа. Node Supervisor — детерминированный эксплуатационный компонент с ограниченными полномочиями.

## 3. Архитектура

### A. Unified Node Supervisor

Локальная Windows-служба на каждом узле.

Отвечает только за собственный компьютер:

- Inventory.
- Local health.
- Installed release.
- Process supervision.
- Service lifecycle.
- Local task execution.
- Disk/resource observations.
- Update preparation.
- Recovery.
- Local logs.
- Durable journal.

Supervisor не избирает лидера, не распределяет глобальные задания и не выдаёт себе полномочия.

### B. Durable Task Journal

Локальный SQLite допустим для записи собственных операций узла.

Использовать:

- Transactional updates.
- Schema versioning.
- Integrity checks.
- Bounded retention.
- Checkpoints.
- Recovery receipts.
- Idempotency.
- Atomic local state transitions.

SQLite не является распределённым consensus.

Глобальная авторизация заданий остаётся за существующим authority.

### C. Deployment Controller

Логический компонент Unified Control Plane.

Использует существующий Scheduler и Consul authority.

Отвечает за:

- Release rollout plans.
- Node admission.
- Compatibility.
- Task assignment.
- Version tracking.
- Health verification.
- Controlled rollback.
- Update history.

Не создавать второй лидерский сервис.

### D. Durable Mission Controller

Новый компонент управления разработкой, не физическим исполнением.

Он должен хранить:

- MASTER MISSION requirements.
- Work items.
- Dependency graph.
- Owners.
- Repository and PR references.
- Exact source SHA.
- CI run/attempt/job.
- Evidence hashes.
- Blockers.
- Approvals.
- Next actions.
- Completion criteria.

Этот компонент не заменяет GitHub или Codex.

Он позволяет восстановить контекст разработки после остановки сессии.

## 5. Автоматизация разработки

Реализовать workflow:

ISSUE DETECTED
→ EVIDENCE CAPTURED
→ OWNER ASSIGNED
→ REPRODUCER CREATED
→ REGRESSION TEST
→ CODE FIX
→ CI
→ INDEPENDENT REVIEW
→ RELEASE CANDIDATE
→ DEPLOYMENT ADMISSION
→ CONTROLLED ROLLOUT
→ RUNTIME VERIFICATION.

Система должна автоматически собирать технические факты, но не утверждать безопасность собственных исправлений.

Разрешённая автоматизация:

- Source inventory.
- Dependency analysis.
- Test execution.
- CI status collection.
- Artifact verification.
- Draft PR preparation.
- Issue classification.
- Evidence indexing.
- Release candidate preparation.

Запрещено автоматически:

- Обходить failed security gates.
- Перезапускать protected single-use operations.
- Подменять native evidence модельными тестами.
- Выполнять merge в main.
- Запускать реальные торговые операции.
- Удалять production data.

## 6. CI Queue Controller

Учитывая текущую проблему Agent 7, реализовать read-only контроль очередей CI.

Хранить:

- Workflow ID.
- Run ID.
- Attempt.
- Job ID.
- Source SHA.
- Queue timestamp.
- Runner assignment.
- Started timestamp.
- Completed timestamp.
- Exit/conclusion.
- Artifact references.
- Authorization state.

Различать:

QUEUED / RUNNING / SUCCESS / FAILURE / CANCELLED / INFRA_BLOCKED / UNKNOWN.

Не считать очередь ошибкой кода.

Не создавать повторный run, если single-use authorization уже использована.

Для Math Agent 7 сохранить исходный run и ожидать его результата без автоматического повтора.

Не выполнять бесконечные polling loops: использовать ограниченную периодичность и backoff.

## 7. Локальная диагностика

Supervisor должен собирать ограниченные сведения:

- Windows edition/build.
- CPU/RAM.
- Disk usage.
- Service status.
- Process exits.
- Application error codes.
- Local connectivity.
- Component versions.
- Queue sizes.
- Checkpoint age.
- Storage health.
- Last successful operation.

Не собирать секреты, приватные ключи, токены или пользовательские документы.

В случае ошибки создавать диагностический пакет с redaction, source/version identity и воспроизводимым контекстом.

Supervisor не должен самостоятельно исправлять произвольные ошибки Windows.

Автоматическое восстановление ограничить заранее утверждёнными действиями.

## 9. Recovery State Machine

Использовать состояния:

CREATED
→ VERIFIED
→ AUTHORIZED
→ PREPARED
→ RUNNING
→ VERIFYING
→ COMPLETED.

Дополнительно:

BLOCKED
FAILED
INTERRUPTED
RECOVERY_REQUIRED
ROLLBACK_REQUIRED
CANCELLED
UNKNOWN_OUTCOME.

После перезапуска:

1. Проверить журнал.
2. Проверить фактическое состояние системы.
3. Проверить authority и fencing.
4. Сопоставить исходное задание с реальным результатом.
5. Продолжить только доказанно идемпотентные операции.
6. Не повторять неопределённую установку или protected execution вслепую.
7. Сохранить оригинальные receipts.
8. Отправить проверенный статус в Control Plane.

Локальные часы не заменяют authority proof.

## 11. Release Management

Создать единый release pipeline:

SOURCE PIN
→ BUILD
→ SIGN/VERIFY
→ TEST
→ INDEPENDENT REVIEW
→ RELEASE MANIFEST
→ NODE ADMISSION
→ STAGED ROLLOUT
→ HEALTH VERIFICATION.

Release manifest должен содержать exact SHA всех шести репозиториев, artifacts, dependencies, schemas и compatibility.

Не обновлять узлы непосредственно из floating GitHub branches.

Использовать immutable packages.

Для каждой версии хранить совместимость с предыдущей и rollback identity.

## 12. Rollout Strategy

Будущий порядок:

1. Disposable Windows test environment.
2. LS5 isolated pilot.
3. PC4.
4. PC3.
5. PC2.
6. PC1.
7. LS7.

Не обновлять одновременно все coordinator nodes.

При обновлении координаторов сохранять необходимый quorum.

Перед изменением worker проверять drain/checkpoint.

При failed health gate останавливать дальнейший rollout.

Не выполнять автоматический destructive rollback.

Не удалять существующие базы или чужие каталоги.
