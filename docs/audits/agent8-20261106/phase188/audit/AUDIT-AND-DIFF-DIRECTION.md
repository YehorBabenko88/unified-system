## Finding: mixed broker capture can pass its own checks; inspected consumer rechecks it

`_policy` reads generation, profile, principal and policy sequentially. `_capture_current` then reads session-lock separately; its final `_context` validates local issuer/socket/deadline/invalidation, not those native records. `_operations_lock` serializes operations on this one broker, not another authorized Consul writer. Individual consistent GETs therefore do not supply one consistent multi-key observation.

INTERLEAVING-RECIPE.json supplies an exact hand-traced data recipe aligned with actual checks, NOT an executed model result: read generationG0/profileF/ACTIVEprincipal; authorized writer changes generationG1, revokes the principal, then updates same policy to ACTIVE revision2 with identical actor/profile/scopes/future expiry; reader reads policyRev2 and unchanged valid principal-session lock. All broker per-field joins and local checks can pass. Returned records combine G0 and ACTIVEprincipal with policyRev2, which first existed only after both ceased being current. The tuple never existed in any one store snapshot. Revision/index changes are real symbolic writes in the proposed model, not claimed actual native writes or public arbitrary-KV permission.

This is a static counterexample to broker atomicity. No actual broker/native/model test was run, and no end-to-end grant exploit is claimed. If API contract only promises independently observed historical records, the behavior must be labelled as such; it cannot be sold as atomic/current multi-record capture. A P1 candidate applies to any caller treating capture alone as atomically current authorization; confirmed executable regression and owner contract adoption remain pending. No P0 demonstrated; no scientific/job/worker grant is enabled in the inspected path.

Important existing guards, not defects to recreate:

* `_open_session` obtains four policy records but already includes their exact check-index operations, leader session/index fence and principal lock creation in one native transaction. A changed generation/principal/policy makes that transaction reject. Sequential pre-reads alone do NOT establish an accepted stale session issuance through this guarded path. Keep its checks.
* `AssignmentAuthority._read_snapshot(keys)` already exists. It uses one Consul read-only transaction with get-or-empty for a bounded unique exact key tuple, consistent query, actual same Consul client/type, exact result count/order/encoding, KnownLeader true and ResultsFilteredByACLs false. Do not duplicate this primitive.
* `ResearchLabAuthority._observe` already calls capture/require, then `_read_snapshot(identityKeys + authorityLeaderKey + jobKey)` and compares EVERY identity record key/index/raw/session. It also checks generation and final local capture. In the hand trace it observes changed generation/principal and rejects CURRENT_IDENTITY_SNAPSHOT_CHANGED. That consumer does not accept this mixed tuple through the inspected path. Its existing submit/lookup results remain negative/UNKNOWN and are not a commissioner or scientific READ API.

`require_capture` performs local checks only; a cached capture can remain locally admissible after an external native change unless a caller rereads/fences. This is a freshness boundary, not fixed forever by an atomic capture. Native revocation immediately after any valid atomic read can still race response delivery. Do not promise continuous validity, UTC at commit, atomic scientific payload visibility or future mutation permission.
