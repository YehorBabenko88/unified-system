# Source-only Collector package builder v1

This tool copies explicit owner-supplied inputs and calls the existing `lab_release.verify_capsule` / `stage_capsule`. It does not execute Python/Git/native programs, import capsule application code, install dependencies, download, infer source provenance, construct an authority or replace the existing verifier. A verified copy is not C0/runnable/runtime/service/provider admission.

## API and canonical recipe

```python
build_package(recipe_path, *, recipe_sha256, work_root, output_root) -> dict
```

Root supplies the exact trusted builder/Unified import path. The tool does not search for another installed verifier or adjust source paths to make an unqualified invocation work. A CLI exposes the same four arguments when the caller's reviewed import context already supplies Unified.

SourceRecipe is canonical JSON using existing `lab_release.canonical` (sorted keys, compact separators, UTF8, final LF). Duplicate keys, nonfinite numbers, unknown recipe keys and hash mismatch reject. Exact fields:

* `schema`: `unified.collector.source-recipe.v1`.
* `manifest`: Root's fully supplied existing **14-key** `unified.lab-release.collector.v1` manifest. Sources, versions, primary commit/tree/blob pins, ordered overlays, dependencies, permissions, runtime, profile and SourceManifest are not invented or normalized by builder. Existing parser/verifier remains the final contract checker.
* `input_roots`: ID → `{path, files, directories}`. Paths are absolute, local, materialized and mutually disjoint; `files` maps relative path to exact `{sha256, bytes}`, and `directories` lists every directory, sorted/unique. Unknown files/directories, symlinks/reparse points, hardlinks, hash drift, unreadable inventory and unsafe relative names reject. A full developer Python installation containing unlisted files is not silently filtered into a selected runtime.
* `members`: final capsule path → `{root, relative, role}`, plus `ledger_path` only for `PYTHON_RUNTIME`. Every manifest member occurs exactly once. Input roots may include explicitly pinned superseded base/overlay files; the final map selects actual bytes. All input bytes, including unused declared base members, remain inside the total input ceiling and exact inventory.
* `runtime_byte_ledger`: `{path, sha256}` pointing at an externally supplied raw JSON object with a `files` map. Each Python runtime member has a unique `ledger_path` key whose exact `{sha256,bytes}` equals selected input/capsule bytes, and all ledger files are used. Supplier path labels are metadata, not a claim the builder independently verified their original origin. Raw ledger bytes/hash are preserved; no normalization or fallback selection.
* `native_source_root_data`: `{path, sha256}` to externally supplied JSON provenance/version data. Builder pins bytes and records `EXTERNAL_NOT_ATTESTED`; it does not mint supplier provenance, binary authenticity, Git version or runtime qualification. Runtime/dependency/Git provenance and actual executable sources remain Root inputs. Python/dependency versions in the manifest are checked only by existing contract rules; inert test metadata never proves a real executable version.
* `limits`: exact positive integers `unified_source_bytes`, `grid_source_bytes`, `total_bytes`, `max_files`. Absolute ceilings56MiB,3.5MiB,512MiB,100000 respectively. Root must supply tighter selected-input budgets for actual assembly. File-count cap applies to aggregate input files as well as capsule members. Total-byte preflight reserves all declared input bytes, external control documents, BOTH retained work/output capsules, both manifests, output recipe/inventory and32KiB for the receipt. It is not merely a per-copy cap. Receipt records declared input/capsule/Python totals and reserved retained logical bytes. This is logical file budgeting, not an OS-enforced physical quota or filesystem allocation/log overhead guarantee; Root still owns broader machine accounting. Metadata documents are capped32MiB before reading them.

Roles are `APPLICATION_SOURCE`, `PYTHON_RUNTIME`, `DEPENDENCY`, `LOCK`, `GIT_TOOL`, `GIT_SUPPORT`, `COLLECTOR_PROFILE`, `SOURCE_MANIFEST`. Source bytes live under the two declared sources; Python bytes under `runtime/python/`; dependencies under `dependencies/`; Git support under `tools/`. Designated profile, source manifest, Git executable and lock paths take precedence and cannot be relabeled as ordinary support/source. Control-role path collisions reject. Ordered overlay final bytes and source SHA256/Git blob OIDs are checked by the existing verifier, not a new Git process or membership authority.

## Effects and retained output

Source roots, NEW work root and NEW output root must be disjoint. Control files cannot be inside either new root. Existing roots are never adopted/overwritten. All inventories/hash/role/budget checks occur before creating work/output. Builder assembles `work_root/capsule`, verifies it, rechecks sources/control pins, then uses existing stage to create `output_root/capsule`. Both trees remain retained; no automatic cleanup, retry, replacement, renaming of active releases or rollback deletion.

Successful output has a verified capsule (only its manifest/files/directories) and separate `source-recipe.json`, `file-inventory.json`, `build-receipt.json` beside it. Receipt gives manifest/recipe/inventory/ledger/supplier hashes, actual declared bytes and flags `execution_authority=false`, `service_admission=false`, `physical_acceptance=NOT_RUN`. No receipt is written before successful staging/verification. A failure leaves any new incomplete roots inactive and retained; a root's existence alone never means complete. No exception is hidden as success. Hash-pinned/exclusive output does not assert OS-enforced immutability against an administrator or power-loss durability of an entire build transaction.
