### 1. Цель

Реализовать первый фактически исполняемый путь между Intelligence Gateway и существующими исследовательскими модулями Unified.

Не открывать публичный submit до прохождения обязательных authority, identity, quota, scheduler и storage gates.

Не создавать новый Scheduler, PaperLedger, Math engine или Experiment Registry.

### 2. Source and ownership

ROOT должен:

1. Проверить текущие exact HEAD/tree всех затрагиваемых репозиториев.
2. Определить актуальную базу Intelligence Gateway PR #44 и связанные PR.
3. Проверить уже существующие target adapters.
4. Назначить владельца файлов.
5. Создать отдельную feature-ветку.

Не использовать старые HEAD из переписки как автоматически актуальные.

### 3. Target Adapter Contract

Создать версионированный контракт, который описывает:

- `request_id`
- `target_kind`
- `target_capability`
- `target_version`
- `dataset_manifest_id`
- `dataset_revision`
- `experiment_id`
- `strategy_version`
- `parameters_digest`
- `execution_mode`
- `resource_budget`
- `quota_owner`
- `principal_id`
- `authority_generation`
- `assignment_revision`
- `fencing_token`
- `idempotency_key`
- `result_schema`
- `result_artifact_ref`

Контракт не должен содержать секреты или произвольные shell-команды.

Наличие этих полей не является доказательством действительной авторизации. Проверять их через соответствующих владельцев.

### 4. Target Capability Registry

Подготовить реестр возможностей существующих исполнителей.

Первоначально:

- Strattester historical backtest.
- Strattester historical replay.
- Math statistical computation.
- MetaAnalyse supported analysis.
- Trader Intelligence offline reconstruction.

Для каждой capability указать:

- Owning repository.
- Exact implementation entrypoint.
- Supported input schema.
- Supported output schema.
- Required dataset.
- Required resource budget.
- Required authority scope.
- Cancellation semantics.
- Recovery semantics.
- Known limitations.

Если реализация отсутствует или не проверена, выставлять `UNAVAILABLE`.

Не создавать фиктивный runtime endpoint.

### 5. Первый исполняемый вертикальный сценарий

Начать с одного полностью изолированного сценария:

**Gateway prepared request → Target Adapter → Existing research implementation → Verified result.**

Рекомендуемый сценарий:

Рассчитать детерминированную статистику по заранее закреплённому синтетическому датасету.

Условия:

1. Данные immutable.
2. Используется существующий исследовательский код.
3. Все входные версии закреплены.
4. Нет доступа к production database.
5. Нет реальных биржевых запросов.
6. Нет настоящих ордеров.
7. Результат воспроизводим.
8. Результат содержит digest и provenance.
9. Повтор одного request_id не создаёт второе выполнение.
10. Ошибки и UNKNOWN сохраняются.

Не подменять реальный target mock-функцией, возвращающей заранее записанный PASS.
